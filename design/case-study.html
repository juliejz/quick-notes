The problem

Small thoughts kept ending up in the wrong place.

During a typical workday, small things appear constantly — todos in meetings, prompt ideas while exploring AI tools, topics to raise in 1:1s, demo credentials shared by colleagues. None of these need a "real" document, but they all need to land somewhere fast and be easy to find later.

Notion felt too heavy (loading screen, sidebar, page hierarchy). Apple Notes mixed work scraps with grocery lists. Stickies couldn't be searched or organized. Every existing tool wanted to be more than I needed.

I wanted something on the Dock, one click away, with zero ceremony — and four small shapes tuned to the four things I actually capture.
Approach

Build the smallest thing that fits four real workflows.

Rather than a general note-taking app, I defined four specific capture contexts and tuned the UI for each:

  • Notes — ad-hoc todos and plain notes from meetings and solo work.
  • Inspiration — AI prompts and reference sites I want to revisit.
  • 1:1 Notes — topics to raise with specific colleagues, grouped by person.
  • Instances — demo environment credentials, for quick copy during a live demo.

A single input box at the top handles all four — typing [ ] task creates a todo, #insp sends it to Inspiration, @name tags it as a 1:1 note. No forms, no modals, no tab switching. The app reads your intent from the text.

A four-tab tool that disappears into the workflow.

Key product decisions

The features I refused to build (and the one I removed).

The product survived by what it said no to. A few of those decisions:

Cut after building
Rich link previews
Built a Slack-style preview card that fetched OG image + title from pasted URLs. Removed it within a week. It broke the product's tone — a fast text scratchpad started looking like Pinterest, depended on network calls, and worked unreliably (many sites block fetching). Cutting it took 5 minutes.

Lesson: "Cool" is not "fits." A well-built feature can still be wrong for the product. Every feature has a tax — speed, simplicity, visual consistency. Ask whether the value pays the tax.
Considered, rejected
Enterprise SSO + OneDrive sync
My boss saw the app and suggested sharing it with more colleagues. The technically obvious path: Microsoft Entra ID + corporate OneDrive instead of personal Google. I chose not to build it.

Reasons: IT approval + security review is high cost; if colleagues adopt it, I become an unofficial maintainer of a personal tool; "your boss likes it" is a signal about craft, not a mandate to ship.

Lesson: distinguish a product from a portfolio piece. Not every well-built thing wants to be scaled.
Bounded configurability
Some routing is NOT user-configurable
The Customize modal lets users rename tabs, reorder, hide, and change routing tags for Inspiration and Instances. But [ ] always means a todo, and @name always means a 1:1 note. Those are hardcoded.

Why: they're not labels, they're behaviour. Letting users rewrite them would invite contradictions in the parser and break the tool's legibility.

Lesson: configurability is good for surface (names, order), bad for grammar (the rules that make the tool make sense).
Architectural default
Local first, cloud second
localStorage is the primary read/write layer — every save is instant and works fully offline. Firebase sync runs as a debounced background write, never blocking the UI. Signed-out, the app is fully functional.

Why: the product's whole value is capture speed. Any model where sync is a requirement would compromise that. Sync is icing, never cake.

Lesson: infrastructure choices encode product values. Defaults matter more than features.
Technical highlights

A few engineering choices worth noting.

The app is intentionally framework-free — one index.html, plain JavaScript, no build step. Optimizing for maintenance cost, not developer ergonomics.

Service worker: split caching by file type

The problem: every index.html deploy was being served from cache, requiring manual CACHE version bumps in sw.js — easy to forget.

The fix: hybrid strategy. index.html uses network-first (fresh deploys appear immediately, cache is fallback); static assets stay cache-first. One cache strategy for everything is the wrong default for PWAs.

Inline hyperlinks: keep the textarea and visual layer separate

Embedding a hyperlink on selected text without showing the raw URL turned out to be unexpectedly hard. The compose box uses a backdrop pattern (transparent textarea + visual overlay), and any approach that stored the URL in the textarea caused invisible characters to displace the cursor.

Final approach: don't change textarea content at all. Store link regions in a side array _pendingLinks = [{start, end, label, url}]; expand to markdown only at submit. Lesson: when a layout layer and an interaction layer have different coordinate systems, don't try to align them — keep them separate.

Test suite: 43 Playwright tests, surfaced a real bug

Wrote a human-readable test plan first, then translated it into 43 automated browser tests covering every user flow. Half the pitfalls were Playwright quirks (clipboard permissions, opacity-based overlays fooling toBeVisible, filter({hasText}) not matching input values).

The valuable one: the test for "duplicate routing tag shows conflict warning" failed — turned out the validation call ran before the draft state was updated. The bug had been live in production for ~9 days. Tests aren't just regression nets; they're a kind of design review.

CI: manual trigger on purpose

GitHub Actions workflow runs Playwright + uploads the HTML report as an artifact (30-day retention). Trigger is workflow_dispatch — manual only — not auto on push. For a solo tool with no real users, auto-CI on every typo commit is noise without value. The artifact gives the "save a test report" benefit without the cost.

Principles that emerged

Five rules I'd carry to the next thing.

  1. Capture speed beats feature richness. Every decision optimized for "open app → typed thought → saved" time.
  2. Local first, cloud second. Sync is additive; nothing depends on it.
  3. Friction is sometimes the feature. Saying no to edit / search / reorder kept the list short and the tool fast.
  4. Build, judge, cut. Some features can only be evaluated after building. The willingness to remove a working feature matters more than the willingness to add one.
  5. Don't scale what doesn't want to scale. A personal tool that helps one person well is more valuable than a half-product that helps many people poorly.
